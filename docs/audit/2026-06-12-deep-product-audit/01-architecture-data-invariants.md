# Architecture, data model, queues, transactions and invariants audit

Дата: 2026-06-12  
Phase: 2 — Review Architecture  
Scope: backend, Telegram bot, Mini App API, workers, Prisma schema, payment/credit ledger, provider adapters, env/deploy assertions.

## Verdict

Архитектура текущей локальной версии выглядит production-oriented и заметно сильнее типичного MVP: есть явные idempotency keys, scoped credit ledger, Postgres queue leases, retry/final-attempt semantics, production env assertions, audit logs, retention fields and tests around the highest-risk money/job invariants.

Но это ещё не "лучший продукт" на уровне операционной зрелости: часть гарантий доказана unit-тестами и schema review, а не live chaos/DB tests; `tests/integration/credits.service.test.ts` был skipped в targeted run из-за недоступной DB. Это не P0, потому что Prisma validate и unit-level invariant tests прошли, но для launch-confidence нужен CI job с реальной PostgreSQL.

## Credit ledger and payment transaction boundaries

| Boundary                       | Status | Evidence                                                                                                               | Notes                                                                        |
| ------------------------------ | ------ | ---------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------- |
| Account concurrency            | PASS   | `CreditsService.lockAccount()` executes `SELECT ... FOR UPDATE` before balance/reserve mutations                       | Protects against concurrent grant/reserve/capture/debit races.               |
| Reserve creation               | PASS   | `reserveWithin()` validates positive amount and sufficient available balance inside transaction                        | Analysis/photo services reserve atomically with job creation.                |
| Scoped capture                 | PASS   | `captureReserve()` checks scoped outstanding reserve for `analysisJobId`, `photoSearchJobId`, or `reportChatMessageId` | Prevents one job consuming another job's reserve.                            |
| Scoped release                 | PASS   | `releaseReserve()` caps by scoped outstanding amount, reserve transaction id, and account reserved units               | Tests cover unknown reserve id and double release.                           |
| Capture + completion atomicity | PASS   | analysis and photo workers call `credits.captureReserve(... within: async tx => update job completed ...)`             | Prevents crash window where paid work is captured but job remains retryable. |
| Non-final retry behavior       | PASS   | workers keep reserve and mark `retrying` before rethrowing; final attempt releases reserve                             | Covered by unit tests.                                                       |
| Payment grant replay           | PASS   | Payment order/event/provider ids are unique and payment service uses idempotent order/event flows                      | Provider details audited in phase 5.                                         |

## Architecture risks

| Severity | Finding                                                                                        | Affected files                                                                                  | Impact                                                                                                              | Recommendation                                                                                               |
| -------- | ---------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| P1       | Integration DB tests were skipped in this run when local PostgreSQL was unavailable            | `tests/integration/credits.service.test.ts`, `tests/integration/_db.ts`                         | Some credit invariants are covered by unit tests and schema review but not by live DB execution in this environment | Add a CI service container for PostgreSQL and make integration credit/payment tests mandatory before launch. |
| P2       | Postgres queue has strong lease semantics but lacks a documented operator playbook             | `src/jobs/postgres-workers.ts`, `src/jobs/recovery.ts`, `fly.toml`                              | On incidents, operators need clear steps for stuck jobs, expired leases, and reserve recovery                       | Add runbook in ops phase with SQL snippets and alert thresholds.                                             |
| P2       | Data deletion/retention architecture exists, but privacy behavior must be validated end-to-end | `src/modules/users/retention.service.ts`, `src/modules/users/user.service.ts`, Prisma relations | Privacy readiness depends on actual deletion/anonymization semantics, not only schema                               | Phase 6 must check deletion flow, retained payment metadata, and audit logs.                                 |
| P3       | Dual queue driver support increases operational surface                                        | `src/jobs/queues.ts`, `src/jobs/postgres-workers.ts`, `src/worker.ts`                           | BullMQ and Postgres paths can drift if both are not continuously tested                                             | Keep one production default (`postgres` on Fly) and ensure both paths have targeted tests or retire BullMQ.  |
